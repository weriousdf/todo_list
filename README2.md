# 만드는 과정 정리

이 앱을 어떤 순서로 만들었는지, 각 단계에서 무엇을 보고 "됐다"고 판단했는지 남긴 기록이다.
결과물 설명은 [README.md](README.md) 에 있다.

## 한눈에

| | 한 일 | 무엇을 보고 넘어갔나 |
|---|---|---|
| 1 | PRD 한 장 쓰기 | 만들 것과 안 만들 것이 적혀 있다 |
| 2 | DB 구조 먼저 설계 | 표·열·관계 그림이 나왔다 |
| 3 | 전체 계획 승인받기 | 6단계와 단계별 확인법이 정해졌다 |
| 4 | SQLite 판 구현 | 단계마다 확인 통과 (최종 검사 21개) |
| 5 | GitHub 에 올리기 | `.env` 와 `todo.db` 가 커밋에서 빠졌다 |
| 6 | Supabase 판으로 이전 | anon 검사 10개 + 계정 격리 직접 확인 |
| 7 | 레포 분리 | 프로젝트마다 별도 저장소 |

## 1. PRD 한 장에서 시작

무엇을 · 어떤 기능을 · 어디에 저장할지 · 어떤 규칙으로 만들지를 한 장에 적었다.
중요한 건 **안 만들 것**도 적었다는 점이다. 안 적으면 알아서 만들어 붙는다.

## 2. 코드보다 DB 구조를 먼저

바로 코딩하지 않고 표·열·관계부터 그렸다. 여기서 한 가지 결정이 나머지를 갈랐다.

**태그를 `todos` 안의 문자열 칸이 아니라 별도 표로 뺐다.** 문자열로 두면
`LIKE '%공부%'` 가 `공부하기` 까지 걸리고, 태그 이름을 바꿀 때 모든 행을 파싱해서
다시 써야 한다. 표 하나 더 만드는 비용이 나중에 되돌리는 비용보다 싸다.

결과는 표 3개다. `todos` (할 일), `tags` (태그 이름의 원본),
`todo_tags` (둘을 잇는 연결표).

## 3. 전체 계획을 먼저 보고 승인

구현 전에 6단계 계획과 **각 단계 끝에 무엇을 확인할지**를 정했다.
이게 이 프로젝트의 핵심 방식이다. "됐습니다" 라는 말 대신 눈으로 볼 수 있는 것을 정해 둔다.

예를 들어 "데이터가 저장된다" 는 확인할 수 없지만,
"서버를 껐다 켠 뒤 목록이 그대로다" 는 확인할 수 있다.

## 4. SQLite 판 구현 — 단계마다 확인

| 단계 | 확인한 것 |
|---|---|
| 폴더·gitignore | `.env`, `todo.db`, `node_modules` 가 커밋 대상에서 빠졌다 |
| DB | 표 3개, 인덱스 2개, 외래키 ON |
| API | 검사 21개 통과. **서버를 껐다 켜도 목록이 그대로** |
| 화면 | 추가·완료·삭제 후 F5 해도 유지 |
| 커스텀 기능 | 마감일 배지, 오늘 필터, 태그 필터, `%` 검색 |

확인을 명령 두 개로 만들어 두었다. `npm run db:check` 와 `npm run api:check` 다.
매번 손으로 눌러보는 대신 명령 하나로 21개를 다시 볼 수 있다.

## 5. GitHub 에 올리기

올리기 전에 무엇이 커밋되는지 목록으로 확인했다.
`.env` 와 `todo.db` 는 규칙에 걸려 빠졌다.

**`todo.db` 를 안 올리는 이유**: 바이너리라 git 이 줄 단위로 비교하지 못하고,
두 기기에서 고치면 병합이 불가능하며, 할 일 목록은 개인 정보이고,
`schema.sql` 로 다시 만들 수 있다. 기준은 "누가 이 파일에 쓰는가" 다.
사용자가 쓰면 데이터라 제외하고, 개발자만 쓰면 자산이라 포함한다.

## 6. Supabase 로 옮기기 — 여기가 제일 많이 배운 곳

같은 앱을 클라우드 Postgres 로 옮기면서 구조가 근본적으로 바뀌었다.

```
SQLite 판    브라우저 → Express → SQLite      막는 곳: 서버 코드
Supabase 판  브라우저 → Supabase (직접)       막는 곳: DB 안의 RLS 정책
```

**RLS 는 로그인이 있어야 의미가 있다.** 정책이 `auth.uid() = user_id` 형태라서
로그인이 없으면 "전부 허용" 아니면 "전부 차단" 둘 중 하나가 된다.
그래서 이메일 로그인을 함께 붙였다.

**anon 키는 공개해도 되는 키다.** 브라우저로 반드시 내려가야 앱이 동작한다.
비밀번호가 아니라 프로젝트 주소표에 가깝다. 다만 그 키의 안전은 키 자체가 아니라
RLS 가 만든다 — RLS 를 안 켜면 주소만 알면 전부 열린다.
`service_role` 키는 RLS 를 통째로 우회하므로 절대 브라우저로 보내면 안 되고,
서버가 시작할 때 그 키인지 검사해서 거부하도록 만들었다.

### RLS 를 어떻게 확인했나

이게 이 프로젝트에서 가장 배울 만한 부분이다. 증거가 세 개 모여야 완성된다.

| 확인 | 결과 | 증명하는 것 |
|---|---|---|
| 로그인 화면 vs 로그인 없는 검사 | 5건 vs **0행** | 바깥에서는 안 보인다 |
| 다른 브라우저, 같은 계정 | 5건 | 데이터가 서버에 있다 |
| 다른 브라우저, **다른 계정** | **0건** | 계정마다 격리된다 |

마지막 줄이 결정적이다. 정책이 "로그인만 하면 다 보임" 이었어도 앞의 두 줄은
똑같이 나온다. 다른 계정에서 비어 있어야 `auth.uid() = user_id` 가 실제로
행을 걸러낸다는 증거가 된다.

쓰기가 막힐 때 나온 오류 코드도 봤다. `42501` 은 RLS 정책이 막았다는 뜻이고,
`23502` 는 `NOT NULL` 제약이 막았다는 뜻이다. 둘 다 "막혔다" 지만
후자는 RLS 의 증거가 아니다.

## 7. 레포 분리

처음에 `hello_test` 안에 커밋했다가 별도 저장소로 뺐다.
이 컴퓨터의 다른 프로젝트들(`blog_BK`, `test_game`)과 같은 방식으로,
폴더는 제자리에 두고 부모의 `.gitignore` 에만 등록한다.

```
프로젝트 폴더에서   git init → 커밋 → gh repo create --source=. --push
부모 저장소에서     git rm -r --cached <폴더>   (--cached 를 빼면 파일까지 지워진다)
                    .gitignore 에 폴더 추가
```

## 부딪힌 함정

**SQLite**
- 외래키가 기본으로 꺼져 있다. 안 켜면 `ON DELETE CASCADE` 가 조용히 동작하지 않는다.
- `DATE` 타입이 없다. 마감일은 `TEXT` 에 `YYYY-MM-DD` 로만 넣어야 정렬이 맞는다.
- `date('now')` 는 UTC 다. 한국 시간 오전 9시 전에는 어제 날짜가 나온다.
- `ORDER BY` 에서 NULL 을 **먼저** 정렬한다.

**Postgres 로 오면서 달라진 것**
- 진짜 `boolean` 과 `date` 가 있어서 우회가 사라졌다.
- `ORDER BY` 에서 NULL 을 **뒤로** 보낸다. SQLite 와 정반대라 `nulls last` 를 명시했다.
- 태그의 `UNIQUE(name)` 을 `UNIQUE(user_id, name)` 으로 바꿨다.
  이름만 유일하게 두면 먼저 '공부' 를 만든 사람이 그 이름을 독점한다.

**그 밖에**
- Git Bash 에서 `curl -d` 에 한글을 넘기면 CP949 로 변환되어 서버에 깨진 값이 도착한다.
  앱 문제가 아니지만 확인 수단으로는 쓸 수 없어서 Node 스크립트로 바꿨다.
- 검색어의 `%` 와 `_` 는 `LIKE` 의 와일드카드다. 이스케이프하지 않으면
  `%` 한 글자에 전체 목록이 나온다.
- `hidden` 속성은 CSS 의 `display: flex` 에 진다. 숨겨둔 요소가 계속 보였다.
- 터미널이 PowerShell 5.1 이면 `&&` 가 동작하지 않는다.

## 다음에도 쓸 만한 방식

1. **코드보다 데이터 구조를 먼저 그린다.** 나중에 바꾸기 제일 어려운 게 이것이다.
2. **계획과 확인 방법을 먼저 정한다.** "됐다" 대신 눈으로 볼 수 있는 것을 정해 둔다.
3. **확인을 명령으로 만들어 둔다.** 손으로 누르는 확인은 다음에 안 하게 된다.
4. **막혔을 때 이유를 구분한다.** 같은 "실패" 라도 원인이 다르면 다른 문제다.
5. **한 번에 하나씩 바꾼다.** SQLite 판을 끝내고 검증한 뒤에 Supabase 로 옮겼다.
   둘을 동시에 했으면 문제가 어디서 났는지 알 수 없었을 것이다.
