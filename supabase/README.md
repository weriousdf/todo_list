# 할 일 (Supabase 판)

`todo_list/` 와 같은 Todo 앱인데, 데이터를 내 컴퓨터의 SQLite 파일이 아니라
Supabase(무료 클라우드 Postgres)에 저장한다. 계정마다 데이터가 분리되고,
분리를 지키는 것은 앱 코드가 아니라 **RLS(행 수준 보안)** 다.

## 두 판의 차이

| | `todo_list/` (SQLite) | `todo_list_supabase/` |
|---|---|---|
| 저장 위치 | 내 컴퓨터 `todo.db` 파일 | Supabase 클라우드 Postgres |
| 로그인 | 없음 | Supabase Auth (이메일 + 비밀번호) |
| 데이터 접근 | 브라우저 → Express → SQLite | 브라우저 → Supabase (직접) |
| Express 의 역할 | API 전부 | 정적 파일 + `.env` 값 전달만 |
| 누가 막는가 | 서버 코드 | **RLS 정책** |
| 다른 기기에서 | 안 됨 | 로그인하면 같은 목록 |

가장 중요한 차이는 마지막 줄이다. SQLite 판에서는 서버 코드를 고치면 무엇이든
할 수 있었다. 여기서는 브라우저가 DB 에 직접 붙기 때문에, `public/app.js` 를
아무리 고쳐도 남의 행은 나오지 않는다. 차단이 DB 안에 있기 때문이다.

## 처음 한 번만 하는 설정

이 부분은 직접 하셔야 한다. 계정 생성과 키 발급은 대신 해 줄 수 없다.

### 1) 프로젝트 만들기

[supabase.com](https://supabase.com) 에 로그인해 **New project** 를 누른다.
지역은 `Northeast Asia (Seoul)` 이 가깝다. 여기서 정하는 **데이터베이스 비밀번호**는
따로 적어 둔다(이 앱에서는 쓰지 않지만, 나중에 DB 에 직접 붙을 때 필요하다).

프로젝트가 준비되기까지 1~2분 걸린다.

### 2) SQL 세 개를 순서대로 실행

대시보드 왼쪽 **SQL Editor** 에서 `sql/` 폴더의 파일을 순서대로 붙여넣고 실행한다.

| 순서 | 파일 | 하는 일 |
|---|---|---|
| 1 | `01_schema.sql` | 표 3개, 인덱스, 수정시각 트리거 |
| 2 | `02_rls.sql` | RLS 켜기 + 정책 11개 |
| 3 | `03_functions.sql` | 목록·추가·태그변경 함수와 실행 권한 |

순서를 지켜야 한다. 2번은 1번의 표가 있어야 하고, 3번은 그 표를 참조한다.

### 3) 이메일 로그인 켜기

**Authentication > Sign In / Providers** 에서 Email 을 켠다.
혼자 쓸 거라면 같은 화면에서 **Confirm email 을 끈다**. 켜 두면 가입할 때마다
인증 메일을 받아야 하는데, 무료 요금제는 시간당 발송 횟수가 적어서 막히기 쉽다.

### 4) 키를 `.env` 에 넣기

**Project Settings > API** 에서 두 값을 복사한다.

```
cp .env.example .env
```

`.env` 를 열어 채운다.

```
SUPABASE_URL=https://<프로젝트ID>.supabase.co
SUPABASE_ANON_KEY=<anon (public) 키>
PORT=3100
```

**`service_role` 키를 넣으면 안 된다.** 그 키는 RLS 를 통째로 우회하므로,
브라우저로 내려가는 순간 누구나 모든 사람의 데이터를 읽을 수 있다.
서버가 시작할 때 키 종류를 검사해서 `service_role` 이면 실행을 거부한다.

## 실행

```
npm install
npm start
```

http://localhost:3100 을 연다. `.env` 가 비어 있으면 화면에 설정 안내가 뜬다.

`todo_list/` 의 SQLite 판은 3000 번을 쓰므로 둘을 동시에 띄워 비교할 수 있다.

## 확인

```
npm run check
```

이 검사는 **로그인하지 않은 채 anon 키만 들고 바깥에서 두드려 보는** 검사다.
아무것도 못 읽고 못 쓰는 것이 정상이다.

- 표 3개가 있는가 (404 면 `01_schema.sql` 을 안 돌린 것)
- 로그인 없이 행이 보이는가 (보이면 RLS 가 안 켜진 것)
- 로그인 없이 쓰기가 막히는가, 그리고 **무엇이 막았는가**
  - `42501` = RLS 정책이 막았다. 의도한 그대로다.
  - `23502` = `user_id NOT NULL` 이 막았다. 막히긴 했지만 RLS 의 증거는 아니다.
- 로그인 없이 `list_todos` 함수를 부를 수 있는가

마지막이 중요하다. **데이터가 하나도 없을 때는 0행이 나와도 증거가 되지 못한다.**
브라우저에서 로그인해 할 일을 몇 개 넣은 뒤 이 검사를 다시 돌려서, 그때도 0행이면
"데이터가 있는데도 바깥에서는 안 보인다"가 되어 RLS 가 실제로 막고 있다는 증거가 된다.

### 화면에서 손으로 확인할 것

| 확인할 것 | 어떻게 |
|---|---|
| 회원가입·로그인 | 이메일과 비밀번호로 가입하면 할 일 화면으로 넘어간다 |
| 세션 유지 | F5 해도 로그인 상태가 유지된다 |
| 기본 CRUD | 추가·완료·삭제 후 F5 해도 유지된다 |
| 마감일 | 어제 마감 항목만 빨간 "지남" 배지 |
| 오늘·태그·검색 | SQLite 판과 동일하게 동작한다 |
| **계정 분리** | 로그아웃하고 다른 이메일로 가입하면 목록이 비어 있다 |
| **태그 분리** | 새 계정에서 같은 이름의 태그를 만들 수 있다 |

마지막 두 줄이 RLS 를 눈으로 확인하는 방법이다.

## SQLite 에서 Postgres 로 오면서 바뀐 것

- `is_done INTEGER 0/1` → `boolean`. 진짜 불리언이 있으므로 `CHECK (x IN (0,1))` 이 필요 없다.
- `due_date TEXT` + `GLOB` 형식검사 → `date`. 진짜 날짜 타입이라 형식이 섞일 수 없다.
- **NULL 정렬이 반대다.** SQLite 는 `ORDER BY x` 에서 NULL 을 먼저 놓고, Postgres 는
  뒤로 놓는다. 같은 쿼리가 다르게 동작하므로 `nulls last` 를 명시했다.
- 수정시각 트리거가 단순해졌다. SQLite 는 `AFTER` 트리거가 자기 표를 다시 `UPDATE`
  해야 해서 무한 재귀를 막는 `WHEN` 절이 필요했지만, Postgres 는 `BEFORE` 트리거에서
  `NEW` 를 직접 고칠 수 있어 그 문제가 없다.
- 태그의 `UNIQUE(name)` 이 `UNIQUE(user_id, name)` 이 됐다. `name` 만 유일하게 두면
  먼저 '공부' 를 만든 사람이 그 이름을 독점한다.
- 트랜잭션이 `BEGIN/COMMIT` 에서 **Postgres 함수**로 옮겨갔다. 브라우저에서 세 표에
  나눠 쓰면 원자성이 없기 때문이다.
